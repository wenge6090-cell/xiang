# 五层认知知识文件系统

**版本：3.0** | **状态：设计完成**

> 本文档描述象（Xiang）项目中五层认知知识文件系统的设计与使用规范。
>
> **设计溯源**：五层递进抽象的思想受 [太极三易.md](./太极agent/太极三易.md) §五 启发——每层是对下一层的提炼和浓缩，形成向上抽象流和向下指导流的双向认知通道。但具体的层定义、引擎交互、文件格式均基于象-三易约束引擎的实际架构设计，而非对太极架构的照搬。

---

## 〇、五层认知金字塔

### 核心思想

五层认知知识文件系统不是简单的"分类存储"，而是一个**认知递进抽象金字塔**：

```
        向上抽象流（执行 → 认知）
  执行日志 → L5经验案例 → L4策略模板 → L3通用规则 → L2关系网络 → L1稳定概念
  ────────────────────────────────────────────────────────────────────────────>
        向下指导流（认知 → 执行）
  L1概念定义 → L2关系理解 → L3规则约束 → L4策略框架 → L5经验借鉴
  <────────────────────────────────────────────────────────────────────────────
```

**向上抽象流**：运行中产生的经验数据，经过提炼逐层向上浓缩，从具体案例逐步抽象为通用概念。
**向下指导流**：每轮执行前，从各层选择性加载相关认知资产，编织进系统提示词，指导 LLM 生成。

### 层级定义

| 层级 | 名称 | 原称（v1.0） | 回答的问题 | 抽象程度 | 演化方式 |
|:----:|------|:-----------:|-----------|:-------:|---------|
| L1 | **概念层** | 事实层 | "这个实体是什么？" | 最低 | 项目演进自然沉淀 |
| L2 | **关联层** | 关联层 | "它和其他概念有什么关系？" | 中低 | 架构调整时同步更新 |
| L3 | **规则层** | 规则层 | "什么情况下该怎么做？" | 中 | 失败分析 → 增量补充 |
| L4 | **策略层** | 策略层 | "如何系统性地思考？" | 高 | 经验沉淀 → 模板固化 |
| L5 | **经验层** | 经验层 | "以前类似情况怎么处理的？" | 最高 | 每轮执行自动积累 |

> 注：v2.0 曾将层级重新定义为"技能/模型/格栅/真理/自我意识"，对齐太极三易.md。v3.0 恢复基于项目实际的层定义，保留太极的"递进抽象"思想。

## 一、各层详细设计

### L1: 概念层 — 领域实体的结构定义

L1 存储项目所涉及的核心概念、术语、对象的**结构化定义**。这是认知金字塔的基石——没有稳定的概念定义，上层所有知识都缺乏锚点。

```yaml
# knowledge/L1_concepts/core_entities.yaml
- name: "归藏 CangVM"
  type: "引擎"
  description: "三易核心执行引擎，基于6-bit卦象状态向量和八气算子的念头流转机器。"
  components: ["Gua 状态向量", "八气算子", "算子队列", "偏离度计算"]
  file: "crates/xiang-cangvm/src/vm.rs"

- name: "八气算子"
  type: "运算单元"
  operators:
    - { name: "生", bit: 0b000001, function: "set_lsb", phase: "生成" }
    - { name: "动", bit: 0b000010, function: "rol_xor", phase: "生成" }
    - { name: "长", bit: 0b000011, function: "lower_to_upper", phase: "生成" }
    - { name: "育", bit: 0b100000, function: "xor_bit5", phase: "生成" }
    - { name: "杀", bit: 0b000110, function: "clear_110", phase: "压缩" }
    - { name: "止", bit: 0b101101, function: "and_mask", phase: "压缩" }
    - { name: "归", bit: null, function: "measure_deviation", phase: "压缩" }
    - { name: "藏", bit: 0b000000, function: "reset_and_store", phase: "压缩" }
```

```yaml
# knowledge/L1_concepts/engine_states.yaml
- name: "偏离度"
  type: "度量指标"
  formula: "Hamming(S, origin) / 6"
  hybrid_formula: "α × hamming + (1-α) × cosine"
  range: [0.0, 1.0]
  thresholds:
    trigger_shanvm: 0.5    # 触发连山障碍导航
    trigger_kill: 0.7      # 触发杀算子终止当前念头
    ideal: 0.3             # 理想上限

- name: "FangWei 方位决策"
  type: "枚举"
  values: ["Continue", "PushThrough", "NavigateAround", "WaitGather", "Decompose", "Escalate", "Abort"]
  source: "xiang-core::lianshan::FangWei"
```

**与三引擎的接口**：

| 引擎 | 读取方式 | 写入方式 |
|------|---------|---------|
| **CangVM** | 加载 L1 → 验证算子定义和状态转换规则 | 不写入（概念层由开发者维护）|
| **semantic_injector** | 加载 L1 → 将核心概念定义注入体系全文 | — |

**演化方式**：不自动演化。L1 是领域知识的基础，随项目功能演进由开发者手动更新。

### L2: 关联层 — 实体间的逻辑关系

L2 存储实体之间的**逻辑关系、依赖、转换规则**。CangVM 的算子状态转换、连山的六步决策链路、ZhouVM 的五行生克都属于 L2 关系。

```yaml
# knowledge/L2_relations/operator_transitions.yaml
- source: "生"
  transitions:
    - { to: "动", condition: "生阶段完成且无异常", type: "正向推进" }
    - { to: "归", condition: "偏离度 > 0.7", type: "杀念回溯" }
    - { to: "止", condition: "重试次数 > max_retries", type: "异常终止" }

- source: "动"
  transitions:
    - { to: "长", condition: "动阶段完成", type: "正向推进" }
    - { to: "生", condition: "阴仪校验失败", type: "rollback" }
```

```yaml
# knowledge/L2_relations/bagua_shengke.yaml
# 五行生克 — ZhouVM 八卦格栅状态转换规则
system: "八卦认知格栅"
relations:
  - { from: "震", to: "离", type: "相生", element: "木生火", description: "收集信息后自然评估" }
  - { from: "离", to: "艮", type: "相生", element: "火生土", description: "审视后收窄聚焦" }
  - { from: "艮", to: "兑", type: "相生", element: "土生金", description: "聚焦后输出表达" }
  # ...
  - { from: "兑", to: "震", type: "相克", element: "金克木", description: "过度输出抑制信息收集" }
```

```yaml
# knowledge/L2_relations/engine_dependencies.yaml
- source: "CangVM"
  depends_on: ["Gua", "八气算子", "偏离度计算"]
  used_by: ["xiang-chat::ConstrainedEngine"]
  interfaces: ["execute_phase_operator()", "judge()", "current_deviation()"]

- source: "ShanVM"
  depends_on: ["FangWei", "SixQi", "SixJia", "SanYuan"]
  triggered_by: "CangVM.deviation > 0.5"
  interface: "run_shan_vm() → LianShanDecision"
```

**与三引擎的接口**：

| 引擎 | 读取方式 | 写入方式 |
|------|---------|---------|
| **ShanVM** | 加载 L2 → 获取六步决策链的关系规则 | 反馈无效关系（调试时）|
| **ZhouVM** | 加载 L2 → 获取五行生克状态转换权重 | — |
| **CangVM** | 加载 L2 → 验证算子转换正确性 | — |

**演化方式**：L2 的关联规则随引擎版本迭代同步更新，通常人为维护而非自动演化。

### L3: 规则层 — 启发式约束与决策规则

L3 存储"如果 X，那么 Y"形式的**结构化规则**。与 L2 的"关系"不同，L3 的规则是**可执行的约束**——阴仪协议规则、连山决策规则都源于 L3。

```markdown
# knowledge/L3_rules/yin_protocol_rules.md

## 生算子输出校验规则
- **必须包含**：试探词（也许/可能/或许/如何）之一
- **必须包含**：问号结尾的疑问句
- **禁止出现**：结构词（第一步/因此/综上所述）
- **建议**：输出长度不超过 200 字

## 动算子输出校验规则
- **必须包含**：发散词（此外/另一方面/还可以/或者）之一
- **禁止出现**：结论词（最终/应该/必须/总之）
- **建议**：至少提出 2 个不同的方向/角度
```

```yaml
# knowledge/L3_rules/lianshan_decision_rules.yaml
- if: "obstruction_count == 0 AND deviation < 0.3"
  then: "Continue"
  confidence: 0.95

- if: "obstruction_count >= 1 AND strategy_verified == true"
  then: "PushThrough"
  confidence: 0.80

- if: "obstruction_count >= 3"
  then: "Decompose"
  confidence: 0.90
  note: "连续三次受阻，需要拆解任务"
```

```yaml
# knowledge/L3_rules/quality_constraints.yaml
- rule: "阴仪校验失败 → 回退重试"
  if: "YinProtocolChecker.check() 返回 Violation"
  then: "CangVM.judge() 返回 CangVMDecision::Rollback"
  max_retries: 2

- rule: "输出重复检测"
  if: "Analyzer.compute_output_deviation() > 0.6"
  then: "CangVM.judge() 返回 CangVMDecision::Skip 当前算子"
```

**与三引擎的接口**：

| 引擎 | 读取方式 | 写入方式 |
|------|---------|---------|
| **CangVM** | 加载 L3 → `YinProtocolChecker` 加载算子规则 | 记录规则匹配成功/失败统计 |
| **ShanVM** | 加载 L3 → `decide()` 参考决策规则 | 反馈新规则候选（高置信度决策） |
| **semantic_injector** | 加载 L3 → 将规则注入动态提示词 | — |

**演化方式**：通过失败分析发现规则盲区，手动补充新规则。ShanVM 的高置信度决策可以根据统计结果自动建议新规则候选。

### L4: 策略层 — 标准化思维框架

L4 存储**可复用的分析框架和思维模板**。不同于 L3 的条件规则，L4 提供的是系统性的思考路径——在认知姿态选定后，为 LLM 提供结构化的"思维脚手架"。

```markdown
# knowledge/L4_strategies/posture_frameworks.md

### 框架：离·审视反思
**适用场景**：输出质量不稳定、需要审查已有成果
**关联姿态**：离（明照）— 温度 0.5
**注入时机**：ZhouVM 选择"离"姿态后，育算子阶段
**步骤**：
1. 逐条审视已有输出，标记不一致之处
2. 对每个标记问："这个结论有依据吗？"
3. 对缺乏依据的结论，标注为"待验证"
4. 输出审查报告 + 修改建议
**提示词片段**：
"请以审视的态度检查之前的输出。对每个关键断言，标注其可信度（高/中/低/无依据）。"
```

```markdown
# knowledge/L4_strategies/decomposition_templates.md

### 框架：连山拆解分解（Decompose）
**适用场景**：三连受阻（SixJia = 三甲）
**关联引擎**：ShanVM 方位决策 = Decompose
**步骤**：
1. 分析当前任务的子目标结构
2. 识别导致卡点的具体环节
3. 将卡点拆分为 2-3 个可独立解决的子任务
4. 按依赖关系排序子任务
5. 从第一个子任务重新开始
```

```yaml
# knowledge/L4_strategies/posture_strategy_map.yaml
# ZhouVM 姿态 → 推荐策略模板的映射
- posture: "震"
  temperature: 0.9
  recommended_framework: "头脑风暴模板"
  goal: "快速收集信息，广泛探索可能性"
- posture: "离"
  temperature: 0.5
  recommended_framework: "审视反思框架"
  goal: "深度审查与质量检查"
- posture: "艮"
  temperature: 0.3
  recommended_framework: "聚焦收窄模板"
  goal: "限定范围，提炼精要"
```

**与三引擎的接口**：

| 引擎 | 读取方式 | 写入方式 |
|------|---------|---------|
| **ZhouVM** | 加载 L4 → 根据当前姿态获取推荐策略模板 | — |
| **ShanVM** | 加载 L4 → Decompose 决策时获取拆解模板 | 反馈策略有效性 |
| **semantic_injector** | 加载 L4 → 将策略模板注入"育"阶段的提示词 | — |

**演化方式**：当一个 L5 案例在类似场景下被反复引用成功，可从中提炼出通用的 L4 策略模板，经人工审核后加入。

### L5: 经验层 — 历史案例与经验教训

L5 存储**完整的成功/失败案例**。这是认知金字塔的输入层——每轮执行的结果在这里沉淀，经过提炼后逐层向上抽象。

```markdown
# knowledge/L5_experiences/debugging_cases.md

### 案例：阴仪校验连续失败后的连山介入
**日期**: 2026-03-15
**场景**: 生算子阶段，LLM 输出未包含试探词
**引擎状态**:
  - 偏离度: 0.45
  - 受阻次数: 2 → SixJia = 再甲
  - 当前算子: 生
  - 当前姿态: 震
  - ShanVM决策: NavigateAround
  - ZhouVM切换: 震 → 离
**处理过程**:
  1. 第1次失败 → Rollback → 重试 → 仍失败
  2. 第2次失败 → ShanVM 触发 → 六甲=再甲 → NavigateAround
  3. 提示词中加入"请以问句形式表达探索性想法"
  4. 第3次成功，偏离度降至 0.2
**关键教训**:
  - 单纯 rollback 不足以让 LLM 调整输出方式
  - 需要在 rollback 时注入针对性的提示引导
  - NavigateAround 后应附带具体的输出风格修改建议
**经验模式**: Rollback + 提示引导联合策略
```

```markdown
# knowledge/L5_experiences/success_patterns.md

### 案例：复杂代码生成任务的最优算子序列
**日期**: 2026-04-02
**场景**: 生成 xiang-cangvm 的 unit test
**最优序列**: 生(实体定义) → 长(框架搭建) → 育(分解子测试) → 动(边缘情况)
**亮点**:
  - 跳过"动"先"长"，避免过早发散
  - "育"阶段拆解为 5 个子测试后，"动"阶段补充了 3 个边缘情况
**成功因素**: 算子顺序的动态调整——非固定 生→动→长→育，而是根据任务类型调整
```

**与三引擎的接口**：

| 引擎 | 读取方式 | 写入方式 |
|------|---------|---------|
| **semantic_injector** | 加载 L5 → 匹配当前状态的高相关案例注入提示词 | — |
| **ShanVM** | 加载 L5 → 匹配类似受阻状态的案例参考经验 | 记录决策结果供提炼 |
| **CangVM** | — | 执行完成后输出日志 → 候选 L5 条目 |

**演化方式**：L5 是**最活跃的层**。每轮执行完成后，通过 CangVM 的执行日志和偏离度变化，自动生成候选案例摘要。高价值案例（偏离度从 >0.5 降至 <0.3 的成功恢复）自动加入 L5，低价值案例定期淘汰。

### 2.2 选择性加载机制

借鉴"虚而待物"思想，不每轮注入全部层级，而是根据**当前引擎状态**按需加载：

```
每轮注入前：
  ┌─────────────────────────────────────────────────────┐
  │ 优先级队列构建                                       │
  │                                                     │
  │ P0（必加载）：                                       │
  │   ├── L1: 当前算子对应的概念定义                      │
  │   └── L3: 当前算子对应的阴仪校验规则                  │
  │                                                     │
  │ P1（条件加载）：                                     │
  │   ├── L2: 当前算子相生/相克关系                      │
  │   ├── L4: ZhouVM 当前姿态对应的策略模板              │
  │   └── L3: ShanVM 当前 SixJia 对应的决策规则          │
  │                                                     │
  │ P2（按需加载 — 仅偏离度 > 0.3 时）：                  │
  │   ├── L5: 偏离度/受阻状态匹配的案例                 │
  │   └── L4: 连山 Decompose 决策对应的拆解模板          │
  └─────────────────────────────────────────────────────┘
```

**注入位置**（对应当前 `semantic_injector` 的 system prompt 组装链）：

```
<|im_start|>system
[三易约束体系全文]          ← 当前硬编码，后续取代为 L1+L3 动态加载
\n\n
[知识注入: L2 关联]        ← 按需注入（仅相关关系）
[知识注入: L4 策略模板]    ← 按需注入（当前姿态对应模板）
\n\n
[动态引擎状态]              ← 运行时状态，保持动态生成
[项目上下文]                ← ProjectContext，保持动态生成
\n\n
[知识注入: L5 参考案例]     ← 仅偏离度高时注入
<|im_end|>
```

## 三、与三易引擎的交互

### 3.1 生成时注入（向下指导流）

```
用户输入
    │
    ▼
┌──────────────────────────────────────────────────────┐
│ 1. ZhouVM 选姿 → 确定当前姿态                         │
│    → 从 L4 加载该姿态对应的策略模板                    │
│ 2. CangVM 确定当前算子                                │
│    → 从 L1 加载算子定义，从 L3 加载校验规则            │
│ 3. 计算偏离度                                        │
│    → 若 > 0.5: ShanVM 触发                           │
│      → 从 L3 加载 SixJia 对应规则，从 L5 加载类似案例 │
│ 4. semantic_injector 组装提示词                       │
│    → P0 层必注入 + P1 层条件注入 + P2 层按需注入      │
│ 5. LLM 生成 → 阴仪校验 → judge()                     │
│ 6. 执行结果 → 记录到 L5 候选日志                      │
└──────────────────────────────────────────────────────┘
```

### 3.2 压缩时沉淀（向上抽象流）

```
一轮执行完成
    │
    ▼
┌──────────────────────────────────────────────────────┐
│ 1. CangVM 藏阶段 → Hebbian 更新（隐式学习）           │
│ 2. 生成执行摘要（偏离度变化、障碍恢复、成功模式）       │
│    → 若偏离度从 >0.5 降至 <0.3：L5 高价值候选         │
│    → 若偏离度持续 >0.5 直至最大重试：L5 失败案例候选   │
│ 3. L5 累计 N 条同类案例 → 提炼 L4 策略模板候选        │
│    → N >= 3 且模式一致 → 生成策略模板 → 人工审核     │
│ 4. L4 策略模板高频使用 → 验证 L3 规则是否更新         │
│    → 模板使用 >10 次且成功率 >80% → 建议固化到 L3    │
│ 5. L3 规则长期无触发 → 淘汰或降级为注释               │
└──────────────────────────────────────────────────────┘
```

### 3.3 各引擎的实际加载点

| 引擎 | 加载函数/时机 | 加载的层 | 当前状态 |
|------|-------------|---------|---------|
| **CangVM** | `execute_phase_operator()` 时 | L1（算子定义）、L3（校验规则） | ✅ 已有硬编码版本 |
| **ShanVM** | `decide()` 决策时（偏离 > 0.5 触发） | L2（关系）、L3（规则）、L5（案例） | ⏳ 需要接入文件系统 |
| **ZhouVM** | `step()` / `select_zhou_pose()` 时 | L4（策略模板） | ⏳ 需要接入文件系统 |
| **semantic_injector** | `build_injection()` 组装提示词时 | L1-L5（选择性加载并注入） | ⏳ 需要从硬编码改为文件加载 |
| **YinProtocolChecker** | `check_operator_output()` 时 | L3（算子规则） | ✅ 已有硬编码版本 |

> ✅ = 当前已可用（硬编码），⏳ = 需要接入文件系统

## 四、认知沉淀闭环设计

### 4.1 沉淀管线

```
每轮执行日志
    │
    ▼
┌─────────────────────────┐
│ L5 候选日志（自动）       │ ← 偏离度恢复/失败案例自动标记
│   · 每轮执行摘要          │
│   · 引擎状态快照          │
│   · 结果标记（成功/失败）  │
└─────────┬───────────────┘
          │ 人工审核（或自动阈值）
          ▼
┌─────────────────────────┐
│ L5 正式条目（手动确认）   │ ← 写入 knowledge/L5_experiences/
│   · 完整案例叙事          │
│   · 关键教训              │
│   · 可复现的条件标记      │
└─────────┬───────────────┘
          │ 模式积累（N >= 3 同类案例）
          ▼
┌─────────────────────────┐
│ L4 策略模板候选          │ ← 从同类 L5 案例提炼
│   · 通用步骤              │
│   · 适用条件              │
│   · 关联姿态              │
└─────────┬───────────────┘
          │ 人工审核
          ▼
┌─────────────────────────┐
│ L4 正式模板              │ ← 写入 knowledge/L4_strategies/
└─────────┬───────────────┘
          │ 高频使用验证
          ▼
┌─────────────────────────┐
│ L3 规则固化候选          │ ← 模板成功率 >80% 且使用 >10 次
│   · IF-THEN 规则          │
│   · 置信度                │
└─────────┬───────────────┘
          │ 人工审核
          ▼
┌─────────────────────────┐
│ L3 正式规则              │ ← 写入 knowledge/L3_rules/
└─────────────────────────┘
```

### 4.2 自动沉淀触发条件

| 条件 | 产出 | 目标层 | 审核要求 |
|------|------|:-----:|---------|
| 偏离度从 >0.5 降至 <0.3 | 成功恢复案例 | L5 候选 | 自动，人工确认后正式化 |
| 连续 3 次重试后失败 | 失败案例 | L5 候选 | 自动，人工确认后正式化 |
| L5 同类案例 >= 3 | 策略模板候选 | L4 候选 | 需人工审核 |
| L4 模板成功率 >80% && 使用 >10 | 规则固化候选 | L3 候选 | 需人工审核 |

### 4.3 当前项目的沉淀现状

当前系统已有部分沉淀机制但未与五层文件系统对接：

| 现有机制 | 对应五层 | 差异 |
|---------|---------|------|
| `CangSea` Hebbian 更新 | 隐含的 L5 | 64×64 权重矩阵，不是结构化案例 |
| `ProjectContext` 决策蒸馏 | L5 弱替代 | 只保留高重要性决策，但无叙事结构 |
| `ContextMetabolism` 输出摘要 | L5 候选日志替代 | 按算子关键词提取，不做案例整理 |
| `SAN_YI_CONSTRAINT_FULL_TEXT` | L1+L3 硬编码 | 固定字符串而非动态文件加载 |

**结论**：五层文件系统的接入不是从零开始，而是将现有的隐式沉淀机制**显式化、结构化**。

## 六、与藏海的分工

> **注意**：当前项目中"藏海"一词涵盖**两个不同层面**的概念。以下分别说明。

### 6.1 代码层面的两个记忆子系统

`CangSea`（`crates/xiang-core/src/cang_sea.rs`）实际上包含**两个独立运行的记忆子系统**，它们与五层文件系统的分工不同：

| 维度 | Legacy CangSea（64×64 Hebbian） | SemanticStore v2（语义向量库） | 五层认知文件系统 |
|:----|:-----------------------------:|:--------------------------:|:--------------|
| **本质** | 隐式状态转移权重矩阵 | 结构化语义经验库 | 显式知识文件 |
| **数据类型** | 64×64 `[[f32; 64]; 64]` 权重 | `SemanticEntry`：5 个嵌入向量（think/goal/obstacle/strategy/attitude）+ reward + deviation | YAML + Markdown 可读文件 |
| **学习方式** | Hebbian 规则：`weight += η × reward` | 相似度合并 + 免疫区隔离 + 经验晶体晶化 | 执行日志 → 人工审核 → 写入 |
| **检索方式** | `query_forces(from)` → push/resist 力 | `query_similar*()` → 余弦相似度 k-NN | 层级优先级 + 关键词 + 嵌入混合 |
| **存储介质** | `weights: [[f32; 64]; 64]`（内存矩阵） | `entries: Vec<SemanticEntry>` + `immune_zone` | `knowledge_base/` 目录（持久化文件） |
| **进化速度** | 每轮自动更新，快速但浅层 | 每轮自动更新，可合并晶化 | 需审核，慢速但深层 |
| **跨模型复用** | ❌ 与 Gua 状态编码绑定 | ⚠️ 部分（嵌入维度依赖模型） | ✅ 完全独立 |
| **可解释性** | ❌ 黑盒权重 | ⚠️ 半结构化（向量不可读，但 reward/deviation 可读） | ✅ 人类可读 |
| **对接引擎** | CangVM 藏阶段写入 / ShanVM `query_forces()` | CangVM `store_semantic()` | 所有引擎 + `semantic_injector` |
| **容量上限** | 1000 entries（FIFO 淘汰低 reward） | 可配置，免疫区独立上限 | 无上限（文件系统） |

**Legacy CangSea** 是"肌肉记忆"——在 Gua 位运算层面学习哪些状态转移是好的。

**SemanticStore v2** 是"情景记忆"——在语义向量空间记录完整的思考轨迹（目标/障碍/策略/姿态），支持相似度检索和模式发现。

**五层文件系统** 是"理性知识"——在人类可读的文本层面沉淀可复用的概念、规则和案例。

### 6.2 与藏海中"多专家池"概念的关系

[07-硬件与藏海架构.md](./07-硬件与藏海架构.md) 中定义的"藏海"是一个**训练/推理架构**概念——用一群独立训练的小模型（1.5B-3B 全量参数专家）替代单一大模型通才，由三易约束引擎动态路由。

这与本文件描述的五层认知知识文件系统**处于不同层面**：

| 层面 | 藏海（多专家池） | 五层认知文件系统 |
|:----|:--------------|:--------------|
| **定位** | 模型架构 — "用什么模型推理" | 知识管理 — "用什么知识武装" |
| **解决的问题** | 通才模型在垂直领域深度不足 | LLM 推理时缺乏结构化知识参考 |
| **实施阶段** | 远期（需硬件升级 + 训练流水线） | 当前可开始建设（文件 + 检索逻辑） |
| **与三引擎的关系** | 底座模型层的替换 | 提示词注入层的补充 |
| **依赖关系** | 可独立于五层文件系统实施 | 可独立于多专家池实施 |

两者**正交**——五层文件系统为所有模型（无论通才还是专家）提供结构化知识注入，多专家池解决的是模型本身的专业能力问题。

### 6.3 交互路径

三者之间的数据流动：

```
Legacy CangSea ──query_forces()──→ ShanVM 障碍导航
      │                                     │
      │ 高奖励经验路径                       │ 高置信度决策模式
      ▼                                     ▼
SemanticStore v2 ──存储/检索──→ 经验向量（目标/障碍/策略/姿态）
      │
      │ 人工审查提炼
      ▼
L5 经验案例 ──→ L4 策略模板 ──→ L3 通用规则  （五层文件系统）
```

> CangSea 练内功（隐性本能），五层库修外功（显性认知）。内外兼修，方为完整的认知进化体。

## 七、与太极三易.md 的关系说明

本文档与 [太极三易.md](./太极agent/太极三易.md) 的关系：

| 方面 | 太极三易.md（原） | 本文档（当前项目） |
|:----|:---------------|:----------------|
| **架构基础** | TPN/DMN 双循环异步架构 | 三引擎同步单循环架构 |
| **L1 定义** | 技能层 — "怎么操作" | 概念层 — "这个实体是什么" |
| **L2 定义** | 模型层 — "什么方式好" | 关联层 — "和其他概念的关系" |
| **L3 定义** | 格栅层 — "什么时候用什么" | 规则层 — "什么情况怎么做" |
| **L4 定义** | 真理层 — "为什么这么做" | 策略层 — "如何系统性思考" |
| **L5 定义** | 自我意识层 — "我是谁" | 经验层 — "以前怎么处理的" |
| **检索执行者** | Weaver（编织器） | semantic_injector（扩展后） |
| **抽象方向** | 向上：数据→智慧 / 向下：智慧→行动 | 向上：执行→认知 / 向下：认知→执行 |

**继承的思想**：
- 递进抽象层级结构（每层是对下层的提炼浓缩）
- 向上抽象流 + 向下指导流的双向流动
- "虚而待物"的选择性加载
- 认知进化的时间维度（做完 N 个任务后比第 1 个时更聪明）

**未继承的概念**：
- TPN/DMN 双循环（当前项目使用同步单循环）
- Weaver/明觉/暗驱/六爻角色（当前项目无对应实现）
- L1 技能层 / L2 模型层 / L3 格栅层 / L4 真理层 / L5 自我意识层定义
